# Config B design (Phase 2) — final revised protocol, for review before pre-registration

**Status:** final revision of 2026-11-09, after the owner accepted the feasibility spike
(`docs/spikes/cage4-feasibility.md`) and set the compute budget. The action-to-family mapping is a draft for
review (`docs/config-b-mapping-draft.md`). **Config B implementation and experiments are not authorized.** No
Config B code, training data or model comparison exists. This protocol is pre-registered and frozen through the
amendment process before the first Config B experiment. Configs C, D and E have not started. CSE-CIC-IDS2018 stays
closed: Phase 5 is a separate, mandatory opening authorization, and nothing here touches it.

## Summary
- **What Config B is.** In the v2 specification, Config B is the static Random Forest of Config A, trained with
  added data from fixed (scripted, non-learning) adversarial scenarios. It isolates "the value of adversarial data
  alone".
- **Decided (owner, 2026-11-09):**
  - **Simulator:** CybORG with the CAGE Challenge 4 scenario, preferred subject to the spike. It is pinned to
    commit `8c3c50ca54b176c2de199847944e8dcc035497e3`, with installed package metadata version `4.0` and the full
    dependency lock in `spikes/cage4/requirements.lock`.
    - CAGE 4's red and green agents are internal, rule-based agents, and the blue team is externally controlled.
      **Config B therefore uses scripted attacker behaviour, not an adaptive attacker.**
    - There is no automatic switch to CybORG++/MiniCAGE. If a critical criterion fails, the work stops and the
      alternatives go to the owner for a separate decision.
  - **Augmentation: "simulator-conditioned flow replay augmentation".** The simulator's action log decides which
    real development records are replayed into training. Nothing here is traffic generated by CAGE, and no sampled
    or perturbed CICIDS2017 or UNSW-NB15 record is described as such. Perturbation is secondary and exploratory.
  - **Arms:** A, B and B0, reported as three contrasts. **B − B0 is primary** for any claim that simulator
    conditioning adds value; B − A is secondary.
  - **Spike accepted** (owner, 2026-11-09), with the compatibility editable install and `pyarrow==17.0.0`, and the
    complete 107-package lock preserved.
  - **Compute budget:** at most 180 CPU-hours, local machine, no GPU, at most two concurrent simulation workers, no
    cloud compute. B0 gets the same nested selection and shortcut audit as B.
  - **Mapping:** drafted from concrete exploits, services, protocols and behaviour, with attempted, failed,
    in-progress and successful actions distinguished. It is not yet frozen.
  - **Revision 2 (owner, 2026-11-09):**
    - **Approved:** `SSHBruteForce` → `brute_force`; `SQLInjection` → `web_attack`, as a broad family-level match;
      both service discoveries → `portscan` (all on improved CICIDS2017).
    - **Provisional:** every UNSW-NB15 entry and `HTTPRFI` → `web_attack`.
    - **Approved:** the outcome rules, and the cap of 4 replays per row (provisionally).
    - **Approved:** the corrected B0 concept.
    - **Compute:** the first compute plan was rejected as over budget.
- **What it can show:** whether **simulator-derived family weighting** of replayed training records (family
  weights from a scripted CAGE 4 scenario's mapped action counts) changes held-out-family recall, at equal
  false-positive rate:
  - against adding the same number of records without the simulator (B − B0);
  - against Config A (B − A).
  - It does not generate traffic, model individual flows, or pick more realistic individual records. It is the "data alone" control for
  RQ1, so that Config C against Config B isolates adaptive co-training.
- **What it cannot show:** anything about adaptive attackers, defender learning, opponent modeling, the realism of
  simulated traffic, or external generalization.

### 1.3 Decision and trade-offs
- **Preferred: CybORG CAGE 4** (owner, 2026-11-09), subject to the spike. It is pinned to the commit above, in an
  isolated environment beside the Aegis one.
  - It is the only candidate where Configs B and C can share one scenario definition and one replay layer. That
    sharing is what lets C against B isolate co-training.
  - Its green agents and blue action costs map to the spec's reward terms (false alarm, disruption, response).
- **What CAGE 4 provides for Config B:**
  - red and green agents are internal and rule-based (`FiniteStateRedAgent`, `EnterpriseGreenAgent`);
  - the five blue agents are externally controlled;
  - **so Config B's attacker behaviour is scripted, not adaptive.** Blue follows a fixed script during scenario
    generation.
- **Costs accepted:** complexity, old gym pins, slow stepping and thin upstream maintenance.
- **No automatic fallback.** If a critical criterion fails, the work stops and the alternatives (including
  CybORG++/MiniCAGE) go to the owner for a separate decision.
- **Secondary environments for Phase 4 (RQ3, cross-environment):** NASim and CyberBattleSim. They are not used in
  Phase 2.
- **For Config B alone, the simulator matters little.** Its attacker is scripted and its defender does not act. It
  is chosen now because B and C must share it.

## 2. Simulator-conditioned flow replay augmentation

### 2.1 Three layers, kept distinct
1. **Simulator state transitions:** abstract changes, for example host H compromised or service S discovered. They
   are ground truth only inside the simulator.
2. **Simulated telemetry:** what the simulator emits about those transitions. In CAGE 4 these are probabilistic
   alerts and analysis results in the blue observations: events, not packets or flows.
3. **Dataset flows:** real CICFlowMeter (improved CICIDS2017) or Argus/Bro (UNSW-NB15) records from the development
   data.

**Neither layer 1 nor layer 2 is network traffic, and CAGE generates no traffic.** The Random Forest consumes only
layer-3 records. A replayed record is a real development record, selected because of a simulated action. It is
never described as traffic generated by CAGE. Every link from an action to a record is a modelling assumption,
stated and checked.

### 2.2 Replay (primary)
- **The mapping** (draft: `docs/config-b-mapping-draft.md`). A pre-registered table maps CAGE 4's concrete
  exploits and scans to development attack families, per dataset.
  - **Evidence:** the concrete exploit, its target service and protocol, and its technical behaviour. Abstract
    categories such as `Impact` are never mapped as such.
  - **Independent justification:** each entry is justified on its own, never by a shared port alone.
  - **Ambiguous actions stay unmapped.** Unmapped actions select nothing, and their counts are reported.
  - **Frozen first:** the table is frozen before any evaluation result of Config B exists.
- **Outcomes** (draft, section 2):
  - each executed concrete action is counted once, on the tick CAGE executes it;
  - in-progress ticks are never counted and never treated as success;
  - failed attempts that contacted a service count as attempts, because they send traffic;
  - exploits that failed before any service was chosen are not counted.
  - Attempted and successful counts are both reported.
- **Allocation in B (simulator-derived family weights):**
  1. For fold seed s, count the mapped events over that seed's scenario episodes, per family (rules O1–O6).
  2. Drop the families that are held out or absent from training. Their events are reported as "excluded: held
     out".
  3. The family weights are p_f = events_f / Σ events over the remaining mapped families.
  4. The requested total is R = r × Σ (training rows of those families), where r is the selected replay ratio.
  5. Family f requests round(R × p_f) replays. These are dealt cyclically without replacement within f.
  6. The cap: at most 4 replays per training row (approved provisionally). The excess is truncated, not
     redistributed.
  7. Requested, realized and truncated counts are reported per family, fold and seed.
  - If no mapped family remains (as on UNSW-NB15 under the approved mappings), B adds nothing, and B = A in that
    fold.
- **The replay pool:** the **current fold's training-partition records** of the mapped family only. Validation
  records, test records and the held-out family are never sampled. An action mapped to the held-out family
  selects nothing in that fold.
- **What replay is:** reweighting and resampling of existing training records, not new observations.
  - A replayed record repeats a record already in the training partition.
  - The effective sample size (Kish) is reported beside the nominal one, per family and for the attack class, and
    no result treats repeats as independent evidence. It never exceeds a family's distinct training rows, and B
    lowers the attack class's effective size (draft, section 4).
  - The simulator decides only which records are repeated, in what proportions.
  - **B cannot supply a held-out family's behaviour.** It reweights seen families toward the scripted attacker's
    mix. B tests whether that reweighting changes recall on an unseen family.

### 2.3 Perturbation (secondary, exploratory)
- **What it is:** replayed records with constrained feature perturbations.
- **Constraints:** non-negativity, integer counts, min ≤ mean ≤ max, totals consistent with counts and means, flag
  counts ≤ packet counts, protocol-specific fields only where valid, and duration consistent with inter-arrival
  times.
- **What constraint satisfaction shows:** only that a record is internally consistent as a flow record. **It does
  not show that the record is an executable attack, or what a real attacker would produce.**
- **How it is reported:** perturbation can create artifacts the model learns as shortcuts. It is reported as
  exploratory, outside every primary contrast.
- **Emulation (not in Config B):** executing scenarios in an explicitly authorized, isolated lab and extracting
  flows with the same extractor is the only route to claims about valid generated traffic. It is deferred, and
  needs its own design and safety review.

### 2.4 Validation of the action-to-record relationship
1. **Mapping audit:** each table entry, with its justification, is reviewed and frozen before any Config B
   evaluation result exists.
2. **Leakage checks**, automated, pass or fail, on every fold:
   - no replayed record comes from validation or test rows, or from the held-out family;
   - no exact feature vector of a replayed record appears in the fold's test rows.
3. **Composition checks:** the family proportions and per-feature distributions of the augmented training set
   against the training partition, with every departure explained by the action mix.
4. **Perturbation checks:**
   - the invariant-violation rate, which must be zero;
   - nearest-neighbour distance to source records;
   - a two-sample classifier, real against perturbed. If it separates them easily, the perturbed records carry
     artifacts and are reported as such.
5. **Simulator-to-dataset correspondence is not validated:** nothing checks that a CAGE alert or action
   corresponds to a recorded flow. This is stated as a limitation.

### 2.5 Claims the data supports
- **Supported:** "a Random Forest trained on its fold's training partition, with existing training records
  replayed under family weights derived from a scripted CAGE 4 scenario's action counts, has held-out-family recall
  X on real dataset flows. This is compared with the same number of records replayed uniformly from the seen
  attack pool (B0), and with no replay (A)."
- **Not supported:**
  - that CAGE produced traffic;
  - that simulated attacks resemble real ones;
  - that perturbed records are valid attacks;
  - that the scenario mix reflects real attacker behaviour;
  - that the method models individual flow behaviour or selects more realistic individual records;
  - any robustness to adaptive attackers.

## 3. Comparison with Config A

### 3.1 Kept identical (directly comparable)
- **Data and splits:** the development datasets (improved CICIDS2017, UNSW-NB15), cleaning, `make_partition` and
  `holdout_fold` with seeds 0–4. The test rows are identical for A and B, because B adds rows to training only.
- **Families:** held-out families with at least 200 cleaned rows. Attempted flows are handled as in Config A.
- **Defender pipeline:** preprocessing, Random Forest settings and fixed-order scoring, all inherited from
  `25685b84dd83f65c`.
- **Thresholds:** the threshold rule (validation-benign quantile), at 1% and 0.1% target FPR. Validation rows are
  unchanged, so B's realized FPR is comparable with A's.
- **Views and metrics:** the three views with raw rows primary; recall, realized FPR, PR-AUC and precision at 1% and
  0.1% prevalence.
- **Shortcut audit:** the same treatments, applied to B. The shortcut rule is unchanged (drop ≥ 0.10 and 95%
  interval above zero), with every comparison counted and no correction.
- **Statistics:** per-seed paired differences, bootstrap intervals (10,000 samples), paired tests and effect sizes.

### 3.2 Arms and contrasts
- **A:** Config A, unchanged.
All three arms train on **exactly the same distinct records**: Config A's training rows for the fold, after
Config A's own per-family cap of 100,000. Replayed copies are added on top of those rows and never displace a real
row, so B and B0 differ from A only in record weights (2.2).

- **A:** Config A, unchanged.
- **B: simulator-derived family weights.**
  - The replay total is split across the mapped, seen attack families in proportion to the scenario's mapped
    action counts (2.2).
  - Records are drawn uniformly within each family, cyclically without replacement, with at most 4 replays per
    row.
- **B0: uniform over the seen attack-record pool.**
  - **Pool:** every attack training record of every family seen in the fold, whether mapped or not.
  - **Draws:** cyclic without replacement over the whole pool, each pass a fresh seeded permutation, with the same
    per-row cap.
  - **Total:** **exactly B's realized total** for the same fold, seed and ratio.
  - **Composition:** family composition is proportional to family size, in expectation and to within one record
    per pass. No simulator information enters.
  - **No mapped family:** where B adds nothing (no mapped family seen), B0 adds nothing either, and both equal A.
- **Correction recorded:** the first draft matched B0 to B *per family*, which would have made B and B0 the same
  procedure.

Three contrasts are reported for every held-out family, as mean per-seed paired differences in raw-view held-out
recall at 1% target FPR, with 95% bootstrap intervals. The interpretations are as the owner set them:

Three contrasts are reported for every held-out family, as mean per-seed paired differences in raw-view held-out
recall at 1% target FPR, with 95% bootstrap intervals:

| Contrast | Measures | Role |
|---|---|---|
| **B − B0** | The value of simulator-derived family composition beyond simply adding records | **Primary** for any claim that simulator conditioning adds value |
| **B − A** | The overall effect of simulator-conditioned replay | Secondary |
| **B0 − A** | The effect of adding replay records without simulator conditioning | Secondary |

- The per-seed difference in degradation (seen minus held out) is secondary, for each contrast.
- Every family is reported, including null and negative results.
- If B ≈ B0, simulator-derived family weighting adds nothing beyond adding records, and that is the finding.
- **No contrast says anything about traffic generation, individual flow behaviour, or record realism.** Within a
  family, B and B0 draw records the same way.
- **Under the approved mappings:**
  - **Improved CICIDS2017:** B's composition differs from B0's mainly in weight. B weights `brute_force`,
    `portscan` and `web_attack`; B0 weights, in proportion to size, mostly `dos`, which is about 90% of the seen
    attack pool when it is not held out.

### 3.3 Data budget and selection
- **Data budget, revised:**
  - Config A's per-family cap of 100,000 applies to the real rows, exactly as in Config A. Replayed copies are
    added on top.
  - All three arms therefore have identical distinct training rows, and no arm gains distinct data.
  - **Why the earlier rule changed:** it applied the cap to real and replayed rows together, so B0's replays into
    `dos` (already at the cap) would have displaced real `dos` rows, and B0 would have lost distinct data.
- **Nested selection, equal rigor (owner, 2026-11-09):**
  - **B and B0 each select their own replay ratio,** from the same candidates (0.25, 0.5, 1.0), by the same inner
    leave-one-family-out on training families only. The rule is Config A's (`aegis.experiments.selection`), fixed
    in advance:
    - **Default:** the first listed candidate, 0.25, the least replay.
    - **Challenger:** a challenger replaces the default only if its mean inner recall at 1% target FPR is higher
      **and** it has strictly higher recall on a strict majority of inner families. Ties on a family count as no
      win.
    - **Several challengers:** among those that pass, the highest mean wins, and ties go to the one listed first.
    - **Matched totals:** in each inner fold, B0 at ratio r adds exactly B's realized total at r.
  - B0 is never given B's choice, and B0's selection is not omitted to save compute.
  - B0's total then follows B's realized total at B0's own selected ratio, so the two arms add the same number of
    records whenever they select the same ratio. If they select different ratios, that is reported, with each arm's
    added total.
  - Outer families are only reported.
- **Shortcut audit:** applied to B and to B0 with the same treatments and rule.
- **Datasets:**
  - **Currently:** under the approved mappings, nothing is mapped on UNSW-NB15, so B = A = B0 there.
  - **If no UNSW-NB15 entry is justified by E1 and E2 before the freeze:** this is reported honestly, and the
    Config B intervention contrasts are limited to improved CICIDS2017. That is a single-dataset result, **not
    cross-dataset validation.**
  - **Evidence comes first:** UNSW-NB15 entries are never forced to make B active on both datasets.

### 3.4 Not directly comparable
- **Simulator-level outcomes** (episode reward, time to detect, containment, response cost):
  - Config A was never evaluated in a simulator.
  - Placing either Random Forest in CybORG as a detector requires the replay map in reverse, so the result
    would depend on that map more than on the model.
  - They are reported only as secondary and simulator-conditional, if at all.
- **Defender actions and costs:** B's defender is static and takes no actions, so operational metrics belong to
  Config C onward.
- **Cross-dataset and cross-environment results:** Phase 4.
- **External results:** Phase 5, through the opening authorization only.

## 3.5 Compute plan, revision 2 (`spikes/cage4/estimate.py`)
**Budget (owner, 2026-11-09):**
- at most 180 **measured** CPU-hours;
- local machine only, no GPU, at most two concurrent simulation workers, no cloud compute.
- **Planning ceiling:** the plan must fit under 153 CPU-h, a 15% safety margin below the budget.

**Why revision 1 was over budget, and what changed:**
- **Rejected:** revision 1 projected 181.6 CPU-h, and the owner did not approve it.
- **Counting error:** the estimate charged nested selection one fit per **ordered** pair of families.
  `aegis.experiments.selection` fits each **unordered** pair once and scores it in both directions, so selection
  was counted twice. Correcting this, not removing anything, brings the plan under the ceiling.
- **Nothing removed:** no control, analysis or candidate is removed. Three ratio candidates are kept, and a fresh
  shortcut audit of A is added.

**What the numbers are:** Phase 1's measured **wall** minutes per fit (improved CICIDS2017 0.76, UNSW-NB15 0.26, at
8 workers), multiplied by 8 cores.
- That is a ceiling, not a measurement: a process on 8 cores cannot use more than 8 CPU-seconds per wall-second.
- Replayed arms are charged for their largest training set.
- **Actual CPU consumption is first measured in the calibration stage.**

| 0 | CAGE 4 scenarios: 50 episodes × 5 seeds, 2 workers | 2.7 | 2.7 |
| 1 | **Calibration:** seed 0 outer folds, A, B and B0. CPU measured. Kept as part of stage 3 | 2.6 | 5.3 |
| 2a | Nested selection of B (3 ratios, one fit per unordered pair) | 25.3 | 30.6 |

- **Margin:** 27.8 CPU-h (15%) below the budget, inside the planning ceiling. Wall time is about 19 hours on 8
  cores.
- **UNSW-NB15:** if nothing is mapped there at the freeze, B and B0 equal A, and their UNSW-NB15 fits are not run.
  The plan above still charges them, as a ceiling.

**Phase 1 evidence, checked against the owner's conditions:**
- **Shortcut audit of A:** not reused.
  - Phase 1's improved-release audit (`results/config_a_artifacts_improved`) has the same data view and
    treatments.
  - But it ran on 2026-11-09 at 00:21, before the re-freeze, under source hash `63f2dd432e59fceb`, not under
    `25685b84dd83f65c`. It scored with multithreaded `predict_proba`, which Phase 1 showed is not bit-for-bit
    repeatable.
  - Its identity is therefore not demonstrably applicable, and stage 4c reruns it.
- **Determinism check:** retained in full.
  - Phase 1 showed that rerunning A under the new identity reproduced every recall and FPR.
  - That is not the required comparison: a same-environment rerun of this experiment's A, B and B0 outputs
    through the Config B code path.

**Measuring CPU:**
- **Main process:** each stage's runner records `resource.getrusage(RUSAGE_SELF)` (user plus system) before and
  after every fit. The Random Forest fits and fixed-order scoring use threads, so all of their CPU is in this
  process.
- **Simulator workers:** separate processes, recorded with `RUSAGE_CHILDREN` after they are joined.
- **Completeness:** at the end of every stage the runner asserts that no child process is still alive, so no CPU
  goes unrecorded.
- **Ledger:** measured CPU per fit and per stage, with wall time, goes to `results/config_b_*/compute_ledger.csv`.

**Stop rules:**
1. **After calibration (stage 1):** compute the measured-to-ceiling ratio per dataset and re-project the remaining
   stages with it. If measured so far plus the projection exceeds 153 (the planning ceiling), stop before stage 2
   and report.
2. **Before every later stage:** re-project the same way. If measured so far plus the remaining projection would
   exceed 180, stop before that stage and report. Above 153 but within 180, report and continue only with the
   owner's approval.
3. **During any stage:** if measured CPU reaches 175, stop at the next fit boundary, so the budget of 180 is never
   crossed, and report.
4. **No silent changes:** no stage, control or analysis is skipped, shortened or reordered silently. Any change is
   the owner's decision.

**Two ratio candidates are not proposed.** They would save 16.7 CPU-h, which is not needed. If they were ever
needed, the candidates would be 0.25 and 1.0, with the same rule and default.
- **Rationale:** they are the ends of the range; the default is the least replay; and dropping the middle loses
  only resolution, not a direction.
- That would be the owner's decision, made before the freeze.

## 4. Research scope
- **Config B tests simulator-conditioned replay augmentation only:** whether replaying the fold's own training
  records in proportions set by scripted CAGE 4 scenarios changes held-out-family recall at equal false-positive
  rate, against unconditioned replay (B − B0, primary) and against Config A (B − A).
- **Its role for RQ1:** it is the "adversarial data alone" baseline. RQ1's claim, that co-training against
  adaptive attackers helps, is tested by C against A and B. A gain of C over B, but not of B over A, would point to
  adaptivity rather than data.
- **It does not test:**
  - adaptive or learning attackers, a learned defender, co-training or the historical league (Config C);
  - opponent modeling (Configs D and E, Phase 3);
  - response effectiveness or cost weights (C onward, Phase 4 sensitivity);
  - generative models (deferred extension);
  - cross-dataset transfer (Phase 4);
  - external generalization (Phase 5).
- **No opponent model, attacker predictor or learned attacker** is built for Config B.

## 6. Risks
| Risk | Effect | Mitigation |
|---|---|---|
| Simulator-to-dataset mismatch | CAGE 4's enterprise topology and abstract actions do not correspond to the CICIDS2017 or UNSW-NB15 testbeds. The action-to-family map is coarse. | Replay uses only real training records. Ambiguous actions stay unmapped. The mapping is justified and frozen. Claims are limited to the feature space (2.5). B − B0 tests whether conditioning adds anything. |
| Reward design | A poorly justified reward would drive Config C later. | Config B does not train on reward. The reward and λ weights are justified and frozen before C, with sensitivity analysis in Phase 4. |
| Unrealistic attacker behaviour | Scripted red strategies and random strategy choice are not real campaigns. | No realism claim. The strategies are frozen and reported. Several fixed strategies are run, and results are reported per strategy if they differ. |
| Environment complexity | CybORG bugs (reported by CybORG++), old gym pins and slow stepping. The spike found two install defects. | Pinned commit and lock, isolated environment, the spike. No automatic fallback: a failure goes to the owner. |
| Schedule (the spec's top risk) | The simulator consumes the phase. | Time-boxed spike. Replay needs only action logs, not simulator changes. No custom simulator. |
| Leakage through replay | Held-out-family, validation or test records enter training. | Automated leakage checks (2.4), on every fold, pass or fail. |
| Repeats mistaken for evidence | Replayed duplicates inflate apparent sample size. | Replay treated as reweighting; effective sample size reported. |
| Shortcuts created by perturbation | Perturbed records teach artifacts. | The shortcut audit applies to B. A two-sample classifier check. Perturbation stays exploratory. |
| More data, not better data | B beats A only through volume. | Data budget, B0, and B − B0 as the primary contrast. |
| Nondeterminism | Results change across environments, as the autoencoder's did. | Pinned versions, a determinism rerun before reporting. No PyTorch model in Config B. |
| Compute | The corrected ceiling is 152.2 CPU-h against 180, and the ceiling is not a measurement. | Calibration measures actual CPU. Re-projection and stop rules apply before every stage, with a stop at 175 measured (3.5). |
| Replay concentrated on tiny families | `web_attack` has 62 training rows, which would be replayed about 16 times each at r = 1. Near-duplicate shortcuts follow. | Per-row replay cap (proposed: 4). Effective sample size reported. The shortcut audit applies to B and B0. |
| Simulator code shapes the mix | CAGE's exploit selector never picks the highest-weight exploit when several apply, so `SSHBruteForce` dominates. | No CAGE change. The behaviour is frozen and reported as a limitation. |
| Upstream defects for Config C | C-1, the intermittent firewall test; C-2, the decoy-path selector `TypeError` (section 1.4). | Neither affects B. Both are resolved or explicitly accounted for before C. |
| Safety | — | Simulation only. Emulation, if ever, only in an explicitly authorized isolated lab. |
